# StarTicket 需求规格说明书

## 1. 产品目标

为演唱会、话剧、展览、脱口秀和校园活动提供活动发布、在线选座、购票、电子票和现场核销能力。

项目必须证明以下能力：

1. 多人同时购买同一座位时，最多一个订单成功。
2. 用户重复提交、消息重复投递、支付重复回调时，业务结果不重复。
3. 未支付订单超时后自动关闭并释放座位。
4. 已支付订单生成唯一电子票，票码最多成功核销一次。
5. 失败任务可重试，超过阈值后进入可查询、可人工处理的失败队列。

## 2. 用户角色

### 2.1 普通用户

- 注册、登录和查看当前账号
- 浏览、搜索活动和查看场次
- 查看票档、座位图和实时座位状态
- 选座、提交订单和模拟支付
- 查看订单、电子票和退款结果
- 在允许时间内取消未支付订单或申请退款

### 2.2 主办方

- 创建和维护活动草稿
- 填写活动海报 URL、介绍和购票须知
- 选择场馆、创建场次、配置票档与价格
- 在草稿或驳回状态编辑、停用场次和票档
- 提交活动审核
- 查看活动订单、票档售出率、退款和净收入

主办方不能自行审核活动，也不能修改已售座位的价格和座位布局。

### 2.3 平台管理员

- 审核或驳回活动
- 按订单号、用户、活动和状态查询全平台订单
- 管理场馆、区域和座位模板
- 查看并重放失败 Outbox 消息

### 2.4 检票员

- 扫描或输入电子票码
- 查询票的有效性
- 执行核销并获取明确结果：成功、已使用、已退款、已作废、场次不匹配

## 3. 核心业务流程

### 3.1 活动发布

```text
主办方创建草稿
→ 配置基本信息
→ 选择场馆和座位模板
→ 创建场次
→ 设置票档和价格
→ 提交审核
→ 管理员通过
→ 在场次销售时间内对外可售
```

活动状态：

```text
DRAFT → PENDING_REVIEW → APPROVED
                 └──────→ REJECTED
```

### 3.2 选座和下单

```text
用户打开座位图
→ 选择可售座位
→ 提交幂等请求
→ Redis 预锁座
→ 数据库条件更新座位状态
→ 创建待支付订单
→ 返回支付截止时间
```

规则：

- 单个订单最多购买 6 张票。
- 同一用户对同一场次最多持有 6 张有效票。
- 锁座有效期默认 10 分钟。
- 同一座位只能属于一个有效订单。
- 用户不得购买已经开始或停止售票的场次。
- 金额以数据库当前票价重新计算，不接受客户端金额。

### 3.3 模拟支付

```text
用户发起模拟支付
→ 支付模块生成支付单
→ 模拟渠道发送回调
→ 校验签名、金额和订单状态
→ 幂等更新支付结果
→ 订单转为已支付
→ 座位转为已售
→ 生成电子票
```

模拟支付保留真实支付需要的支付单号、渠道流水号、签名校验、异步回调和重复通知处理，不接入真实资金渠道。

### 3.4 超时关闭

```text
订单创建
→ 发送延迟消息
→ 到期检查订单状态
→ 仍待支付则关闭订单
→ 数据库释放座位
→ 删除或自然过期 Redis 锁
```

延迟消息可能重复，因此关闭订单和释放库存必须幂等。定时补偿任务负责扫描少量超时但未关闭的订单。

### 3.5 电子票与核销

- 每张订单项生成一张电子票。
- 票码使用不可预测的随机令牌，不直接暴露订单号或用户ID。
- 前端将票码渲染为二维码。
- 核销以数据库条件更新作为最终判断。
- 重复扫描返回“已核销”，不得再次记录成功核销。
- 已退款、已作废或场次不匹配的票不能核销。

### 3.6 取消与退款

- 待支付订单可以直接取消并释放座位。
- 已支付订单在场次开始前 24 小时可申请模拟退款。
- 首版只支持整单退款，不支持部分退票。
- 退款成功后订单转为已退款、电子票作废、座位恢复可售。

## 4. 状态定义

### 4.1 场次座位

```text
AVAILABLE → LOCKED → SOLD
     ↑          │
     └──────────┘ 取消或超时
     ↑          │
     └── SOLD ──┘ 退款成功
```

### 4.2 订单

```text
PENDING_PAYMENT → PAID → REFUNDING → REFUNDED
       │             │
       ├→ CANCELLED  └→ CLOSED（仅异常人工关闭）
       └→ EXPIRED
```

### 4.3 电子票

```text
VALID → USED
  ├──→ REFUNDED
  └──→ VOID
```

## 5. 功能优先级

### P0：必须完成

- 注册、登录、JWT鉴权和角色权限
- 场馆、区域、座位模板管理
- 活动、场次、票档和审核
- 活动列表、详情和座位图
- 选座、锁座、创建订单
- 模拟支付和支付回调
- 超时关单及释放座位
- 电子票生成和单次核销
- 未支付取消、整单模拟退款
- Docker Compose 一键启动
- OpenAPI 接口文档

### P1：简历增强项

- Redis Lua 原子预锁座
- RabbitMQ 延迟关单、重试和死信队列
- Outbox 保证数据库事务与消息最终一致
- 请求幂等键和状态条件幂等消费
- 热点活动缓存与缓存失效
- 接口限流
- Actuator、Prometheus、Grafana
- Testcontainers 集成测试
- k6 并发压测报告
- GitHub Actions 自动构建和测试
- 活动与订单服务端搜索分页、销售统计和运营订单查询

### P2：明确延后

- 真实支付渠道
- 分库分表和多级缓存
- 微服务、注册中心和分布式事务框架
- 优惠券、会员等级和复杂营销
- 动态定价、候补队列和票务推荐
- 短信、邮件以及对象存储服务
- 多语言和多币种

## 6. 非功能需求

### 6.1 一致性

- 任意并发测试中售出数量不得超过场次配置库存。
- 订单总金额必须由服务端根据订单项价格快照计算。
- 支付成功、座位售出和电子票生成最终一致。
- 所有状态迁移必须校验当前状态，禁止任意覆盖。

### 6.2 幂等

以下操作必须幂等：

- 创建订单：`Idempotency-Key + userId`
- 支付回调：渠道流水号或支付单号
- 超时关单：订单号
- 超时关单：订单号 + 当前状态条件更新
- 核销：电子票ID
- 退款回调：退款单号

### 6.3 安全

- 密码使用 BCrypt 存储。
- 接口使用 RBAC 鉴权，主办方只能管理自己的活动。
- 下单接口使用 Redis 窗口计数限流。
- 不在日志中输出密码、JWT、支付签名和完整票码。
- 金额使用 `BigDecimal`，数据库使用 `DECIMAL(10,2)`。
- 所有外部输入进行格式、长度和业务校验。

### 6.4 性能验收

性能数字以最终压测报告为准，不提前在简历中宣称。开发阶段设定以下验收目标：

- 指定 4 核 8 GB Docker 环境并记录全部参数。
- 热门活动详情接口在 500 并发下无服务端错误。
- 抢购固定库存时，最终售出量精确等于库存量，不超卖。
- 输出吞吐量、平均延迟、P95、P99、错误率和资源使用率。
- 分别比较“仅数据库条件更新”和“Redis 预锁 + 数据库确认”两种方案。

### 6.5 可运维性

- 提供健康检查、核心指标和结构化日志。
- 记录下单成功率、锁座失败率、支付回调失败数、超时订单数、核销成功数和死信数量。
- Docker Compose 能一次启动应用依赖。
- 数据库结构由 Flyway 管理，禁止依赖手工建表。

## 7. 验收场景

1. 100 个用户并发购买 10 个座位，最终最多 10 个订单成功且无重复座位。
2. 同一个 `Idempotency-Key` 重复提交，返回同一业务结果。
3. 支付回调发送 5 次，只生成一笔成功支付和一组电子票。
4. 待支付订单到期后自动关闭，座位重新可购买。
5. 已支付订单不会被超时消息关闭。
6. 同一电子票并发核销两次，只有一次成功。
7. 已退款电子票不能核销，座位重新可售。
8. 主办方不能修改其他主办方的活动。
9. 普通用户不能调用审核、核销和场馆管理接口。
10. RabbitMQ 暂时不可用时，已提交的业务事务不丢失，恢复后可补发消息。
