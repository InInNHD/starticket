# StarTicket 性能测试报告

## 环境

- 日期：2026-08-28
- CPU / 内存：AMD Ryzen 7 5800H（8 核 16 线程）/ 16 GB
- JDK 21.0.12、MySQL 8.4、Redis 7.4、RabbitMQ 4
- 后端：本机 Java 进程；基础设施：Docker Desktop 29.7.2
- 负载：每轮 100 个同时请求，20 个独立账号竞争同一座位，每种方案 3 轮
- 统计：3 轮算术平均；409 座位冲突为预期业务结果，不计入技术错误

## 对比结果

| 方案 | 吞吐量 | 平均延迟 | P95 | P99 | 错误率 | 是否超卖 |
|---|---:|---:|---:|---:|---:|---|
| MySQL 条件锁座 | 95.45 req/s | 854.44 ms | 967.27 ms | 977.15 ms | 0% | 否（PASS） |
| Redis Lua 预锁 + MySQL 确认 | 81.35 req/s | 1196.75 ms | 1248.48 ms | 1255.97 ms | 0% | 否（PASS） |

每轮均恰好 1 个请求创建订单，其余 99 个返回 409。压测后执行 `load/assert-no-oversell.sql`，座位 10–15 的有效订单数均为 1，全库重复售出断言为 `PASS`。原始汇总保存在 `load/mysql-summary*.json` 和 `load/redis-summary*.json`。

## 结论

在本机、100 并发的单座位竞争下，MySQL 条件更新方案更快；Redis 预锁多了一次网络往返，吞吐量低 14.8%，P95 高 29.1%。这说明 Redis 不应仅为了“高并发”标签引入；当热点流量足以压垮数据库、需要跨实例削峰时，才能用降低数据库写竞争来换取整体系统容量。无论 Redis 是否启用，MySQL 条件更新仍是最终一致性防线。
