# StarTicket 性能测试报告

## 测试结论

2026-08-30 在固定 4 vCPU / 8 GB 服务端预算下完成 18 轮正式库存测试。预热使用 300 个专用用户和独立场次；每轮正式测试使用另外 1000 个独立用户、未被访问的完整库存和固定 1000 次请求，结果取三轮中位数。

- 单座位竞争中，两种方案都只成功售出 1 张；Redis 的 139.62 req/s 主要是 `409` 冲突吞吐，不能表述为成功下单能力。
- 100 座位限量销售中，Redis 路径成功下单吞吐为 19.39 req/s，MySQL-only 为 21.38 req/s，Redis 约低 9.3%。
- 1000 个分散座位中，请求全部成功；MySQL-only 为 214.34 req/s，Redis 路径为 193.80 req/s，Redis 约低 9.6%。
- 18 轮的 `429`、`5xx`、传输错误和重复座位均为 0；最终售出数与场景库存完全一致，SQL 全局断言为 `PASS`。

旧压测在预热阶段已经售空正式场次，300 并发热点结果全部为 `409`，所以旧“Redis 吞吐提升 41.8%”结论无效，本报告不再保留该数字。

## 环境

服务端使用专用 [`load/compose.perf.yml`](../load/compose.perf.yml)，负载发生器运行在容器外，不计入服务端预算。完整机器可用资源不参与口径，比较只依据容器硬限制。

| 服务 | CPU 上限 | 内存上限 |
|---|---:|---:|
| Spring Boot | 2.00 vCPU | 2048 MB |
| MySQL 8.4 | 1.25 vCPU | 3072 MB |
| Redis 7.4 | 0.25 vCPU | 512 MB |
| RabbitMQ 4 | 0.50 vCPU | 1536 MB |
| **容器合计** | **4.00 vCPU** | **7168 MB** |

其余 1 GB 作为 Docker 运行开销预留。后端使用 Java 21、`-Xms512m -Xmx1g -XX:+UseG1GC`，HikariCP 最大连接数为 10。数据规模为 300 个预热用户、1000 个正式用户、5000 个场馆座位、36 个场次和 18 万条场次座位快照。环境快照记录了容器实际限制、Git 提交号、JVM 参数和复现命令，见 [`performance-environment.json`](../load/results/performance-environment.json)。

## 方法

对比两条锁座路径：

1. `MySQL-only`：直接执行带状态条件的库存更新，以数据库作为并发闸门；
2. `Redis + MySQL`：先用 Redis Lua 原子预锁，再由相同的 MySQL 条件更新最终确认。

每种方案执行三个明确场景，每个场景 3 轮：

| 场景 | 可售座位 | 正式请求 | 期望结果 |
|---|---:|---:|---|
| `SINGLE` | 1 | 1000 | 1 个 `201`，999 个 `409` |
| `LIMITED` | 100 | 1000 | 100 个 `201`，900 个 `409` |
| `SPREAD` | 1000 | 1000 | 1000 个 `201` |

所有正式轮次均为 300 并发，每个请求使用一个未参与预热的独立用户。每轮先由预热用户向另一个场次发送 300 次请求，正式场次在计时开始前保持完整库存。吞吐量按固定请求数除以实际墙钟时间计算，并分别统计成功下单吞吐、业务冲突吞吐、`201/409/429/5xx`、最终售出数、重复座位和超卖数。

## 库存场景结果

以下均为三轮中位数：

| 场景 | 方案 | 总吞吐 | 成功吞吐 | 冲突吞吐 | `201 / 409 / 429 / 5xx` | 售出 / 重复 / 超卖 |
|---|---|---:|---:|---:|---:|---:|
| 单座位 | MySQL-only | 150.68/s | 0.15/s | 150.53/s | 1 / 999 / 0 / 0 | 1 / 0 / 0 |
| 单座位 | Redis + MySQL | 139.76/s | 0.14/s | 139.62/s | 1 / 999 / 0 / 0 | 1 / 0 / 0 |
| 100 座位限量 | MySQL-only | 213.75/s | 21.38/s | 192.38/s | 100 / 900 / 0 / 0 | 100 / 0 / 0 |
| 100 座位限量 | Redis + MySQL | 193.89/s | 19.39/s | 174.50/s | 100 / 900 / 0 / 0 | 100 / 0 / 0 |
| 1000 分散座位 | MySQL-only | 214.34/s | 214.34/s | 0/s | 1000 / 0 / 0 / 0 | 1000 / 0 / 0 |
| 1000 分散座位 | Redis + MySQL | 193.80/s | 193.80/s | 0/s | 1000 / 0 / 0 / 0 | 1000 / 0 / 0 |

| 场景 | 方案 | 平均延迟 | P95 | P99 | 平均进程 CPU | 最大堆 | 最大 DB 连接 |
|---|---|---:|---:|---:|---:|---:|---:|
| 单座位 | MySQL-only | 1749.04 ms | 2916.20 ms | 3405.12 ms | 60.74% | 375.48 MB | 10 |
| 单座位 | Redis + MySQL | 1891.05 ms | 3397.43 ms | 4312.63 ms | 33.88% | 376.48 MB | 10 |
| 100 座位限量 | MySQL-only | 1237.32 ms | 2091.66 ms | 2685.74 ms | 53.01% | 374.75 MB | 10 |
| 100 座位限量 | Redis + MySQL | 1369.69 ms | 2329.05 ms | 3045.14 ms | 33.37% | 359.96 MB | 10 |
| 1000 分散座位 | MySQL-only | 1218.70 ms | 2004.97 ms | 2215.83 ms | 54.07% | 367.25 MB | 10 |
| 1000 分散座位 | Redis + MySQL | 1351.99 ms | 2206.62 ms | 2433.79 ms | 24.16% | 369.20 MB | 10 |

在单座位场景中，99.9% 请求是预期冲突，总吞吐只能说明系统拒绝冲突的速度。100 座位场景同时包含有限的成功交易和大量冲突，Redis 的成功吞吐仍下降约 9.3%；1000 个分散座位中下降约 9.6%。在当前单实例和数据规模下，额外 Redis 往返没有抵消其成本。因此默认路径保持 MySQL 条件更新；只有通过真实流量证明数据库热点成为瓶颈时，才设置 `STARTICKET_REDIS_PRELOCK_ENABLED=true` 启用 Redis 预锁。

完整聚合数据见 [`benchmark-summary.json`](../load/results/benchmark-summary.json)，每轮 JSON 保留在同一目录。

## 一致性断言

每个正式场次结束后立即验证售出数量、去重座位数和场景库存；18 轮完成后再执行全局 SQL：

```text
formal_inventory_assertion
PASS
duplicate_seat_assertion
PASS
```

详细逐场次结果见 [`benchmark-consistency-assertion.txt`](../load/results/benchmark-consistency-assertion.txt)。Redis 预锁成功不代表订单成功，MySQL 条件更新和唯一约束仍是两条路径共同的最终一致性防线。

## 热门活动详情验收

同一受限环境下，对公开活动详情 `GET /api/events/1` 执行 500 并发、10 秒预热、每轮 30 秒正式负载，共 3 轮：

| 轮次 | 请求数 | 吞吐量 | 平均延迟 | P95 | P99 | HTTP 状态 |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 9708 | 310.16/s | 1582.34 ms | 2395.82 ms | 2998.70 ms | 全部 200 |
| 2 | 11855 | 381.24/s | 1290.66 ms | 1988.01 ms | 2491.70 ms | 全部 200 |
| 3 | 15205 | 488.68/s | 1006.47 ms | 1593.51 ms | 1992.93 ms | 全部 200 |
| **中位数** | **11855** | **381.24/s** | **1290.66 ms** | **1988.01 ms** | **2491.70 ms** | **全部 200** |

三轮共 36768 次正式请求，无 `5xx` 和传输错误，满足当前“500 并发下无服务端错误”的验收条件。该结果仅代表固定资源下的单实例开发环境，不是生产容量承诺。

## 复现

```powershell
./load/Prepare-Sustained.ps1
./load/Run-Sustained.ps1
```

第二个脚本结束后会删除专用压测卷并恢复默认 demo。若中途停止，可手动执行 `./load/Restore-Demo.ps1`。测试命令、原始 JSON、SQL 断言和资源快照均随仓库保存，便于检查结论而不是只看 README 数字。
