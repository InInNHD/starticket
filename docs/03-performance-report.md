# StarTicket 性能测试报告

## 测试目标

对比两条锁座路径在热点与非热点负载下的真实表现，并确认所有方案最终都不超卖：

1. MySQL 条件更新：直接执行带状态条件的库存更新，由数据库作为并发闸门；
2. Redis Lua 预锁 + MySQL 确认：先在 Redis 原子预占，再进入数据库事务完成最终确认。

## 环境与方法

- 日期：2026-08-29
- 主机：Windows 11，AMD Ryzen 7 5800H（8 核 16 线程），15.9 GB 内存
- 运行时：JDK 21.0.12、Docker Desktop 29.7.2、MySQL 8.4、Redis 7.4、RabbitMQ 4
- 应用：单个 Spring Boot 容器，HikariCP 最大连接数 10
- 数据：600 个独立用户、5000 个座位、36 个独立场次、18 万条场次座位快照
- 并发：20 / 100 / 300；每组预热 10 秒、持续 30 秒、执行 3 轮
- 模型：`HOTSPOT` 始终竞争同一座位；`SPREAD` 轮询 5000 个不同座位
- 统计：表内数值取三轮中位数；409 库存/限购冲突属于预期业务结果，技术错误率只统计其他响应

测试使用 `load/Prepare-Sustained.ps1` 和 `load/Run-Sustained.ps1` 一键完成数据准备、方案切换、负载执行、指标采集、结果聚合与 demo 服务恢复。原始结果保存在 `load/results/`。

|---|---:|---:|---:|---:|---:|---:|---:|---:|
| MySQL | 20 | 612.15 req/s | 32.61 ms | 51.25 ms | 71.74 ms | 28.31% | 201.32 MB | 0% |
| Redis + MySQL | 20 | 724.91 req/s | 27.53 ms | 46.83 ms | 60.62 ms | 32.74% | 168.42 MB | 0% |
| MySQL | 100 | 537.13 req/s | 185.73 ms | 318.94 ms | 442.79 ms | 20.80% | 216.08 MB | 0% |
| Redis + MySQL | 100 | 720.23 req/s | 138.58 ms | 265.78 ms | 354.42 ms | 27.48% | 202.30 MB | 0% |
| MySQL | 300 | 571.32 req/s | 517.91 ms | 786.32 ms | 1105.26 ms | 19.48% | 216.50 MB | 0% |
| Redis + MySQL | 300 | 810.01 req/s | 368.12 ms | 665.97 ms | 840.18 ms | 25.87% | 211.83 MB | 0% |

热点负载下，Redis 预锁在 20 / 100 / 300 并发分别提升吞吐约 18.4% / 34.1% / 41.8%，P95 分别下降约 8.6% / 16.7% / 15.3%。原因是大量失败竞争在 Redis 中被提前拒绝，减少了进入数据库事务和争抢热点行锁的请求。

## 一致性断言

每轮使用独立场次，完成后执行 `load/assert-no-oversell.sql`。所有有效订单均满足：

```text
no_oversell
PASS
```

热点场次最多只有 1 个有效订单；分散场次的 `sold_items` 与 `distinct_sold_seats` 始终相等。MySQL 条件更新仍是两种方案共同的最终一致性防线，Redis 只承担热点削峰，不作为唯一库存事实来源。

## 结论与边界

- 热点明显时启用 Redis Lua 预锁，可以减少数据库无效竞争并改善吞吐和尾延迟；
- 普通分散售票直接使用 MySQL 条件更新更简单且更快，不应只为“高并发”标签强制经过 Redis；
- 20 → 100 → 300 并发的吞吐没有线性增长，300 并发下 P95 普遍接近或超过 1 秒，当前单实例的合理限流点应低于 300；
- 本报告是单机开发环境结果，适合比较方案相对差异，不等价于生产容量承诺；生产评估还需增加多实例、网络延迟、真实流量分布和长时间稳定性测试。
